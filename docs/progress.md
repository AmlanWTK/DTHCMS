| CP35 | Patient edit & demographic correction        | **Done**   | `PATCH /v1/patients/{id}` and `GET /v1/patients/{id}/history`. A correction is an event, never an overwrite: what the value was, what it is now, and why, with the original left in the ledger. Every request field is a pointer and `nil` means _not touching this_ — a form that renders six fields and posts all six would otherwise rewrite five of them with whatever it had loaded, which is how a stale tab silently reverts a colleague's work. A correction that changes nothing is **refused** rather than recorded as a no-op, including a telephone number retyped in a different format, which normalises to no change; so is one with no usable reason. Both rules also hold in the database (`assert_corrections_are_explained()`), so an unexplained correction cannot exist however it was written. The date of birth, its precision, the sex and the English name are **high-impact** and demand a step-up (`patient_correct_identity`) on top of the write permission — the plan asks for "elevated permission", the catalogue has no code for it, and the real risk is a session left open on a desk rather than a person who should never have had the capability; because whether one is needed depends on _what changed_, the check sits in the handler and not on the route. `ops.derived_dependency` is the plan's risk note made explicit: a register of which derived values depend on which fields, so the read model, the phonetic search key and the anonymised cohort row all move in the same transaction and the next derived value somebody adds is declared rather than discovered by a patient whose percentile never updated. A retried correction produces one event and one history row. The screen is a **diff, not a form**: changed fields are marked, the previous value is printed under each one, and the button names how many fields will change rather than only greying out.
